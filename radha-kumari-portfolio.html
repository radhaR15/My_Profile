    Multi-carrier SIM activation and provisioning platform

    C#, ASP.NET Core, .NET Web API, Entity Framework, LINQ, SQL Server. Used across T-Mobile, BOOM Network, SURF, Linkup and Xtream.

    The problem

    When a customer buys a SIM, the number has to be validated, a plan attached and the carrier asked to switch the line on. Each carrier has its own API and its own responses, and a retailer needs one reliable system on top that records exactly what happened. A failed or duplicated activation costs money and leaves the subscriber without service.

    How an activation moves through the system

    Select a stage to see what my code does there.

    What I own

    • The activation workflows in C# and ASP.NET Core, from first request to final status.
    • The RESTful APIs that accept activation requests and the integrations that call each carrier.
    • The SQL Server tables, joins and stored procedures that store every transaction and make it traceable.

    What it delivers

    A single, consistent activation process across several carriers, with transaction data that Support and Business teams can trust, and fewer failed activations because problems are found and fixed at the source.

    Commission, spiff and residual processing

    SQL Server, stored procedures, query optimization, data validation.

    The problem

    Sales partners are paid for activations through commissions, one-time spiffs and ongoing residuals. If an activation record is wrong, the payout is wrong, and someone has to find out why.

    What I built

    • Complex SQL queries, joins and stored procedures that calculate commission, spiff and residual amounts from activation data.
    • Validation checks that compare activation records against payout records before they reach the business.
    • Query tuning with indexes and cleaner joins so the calculations stay fast as data grows.

    What it delivers

    Payout figures that match the underlying activations, and a clear way to trace and resolve any discrepancy.

    Failed-activation investigation and reconciliation

    SQL Server, API debugging with Postman and Swagger, Azure DevOps.

    The problem

    Even a well-built flow fails sometimes: a carrier times out, a request is sent twice, or a record and its carrier status disagree.

    How I work through it

    • Trace the transaction through its lifecycle, using the API response and the database record side by side.
    • Find the cause: a failed carrier response, a duplicate transaction or a data mismatch.
    • Fix the code or correct the data, then add a reconciliation check so the same issue is caught earlier next time.
    • Work with QA, Support and Business teams so the fix matches what they see in the field.

    What it delivers

    Higher activation success rates and consistent, reliable subscriber records.

    Recharge flow

    C#, .NET Web API, SQL Server. Same multi-carrier approach as activation.

    The problem

    A recharge adds balance or a plan to a line that is already active. The money, the carrier and the subscriber's balance all have to agree, so a request that half-succeeds is worse than one that fails cleanly.

    How a recharge moves through the system

    • Validate the subscriber's number and confirm the line can be recharged.
    • Confirm the plan or amount, and check payment before the carrier is called.
    • Call the carrier's recharge API and validate the response, handling success and failure separately.
    • Save the final status and transaction in SQL Server so it can be traced and reconciled later.

    What it delivers

    Recharges that are recorded exactly once and can be traced from request to carrier response.
